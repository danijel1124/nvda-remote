# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Server-specific guidance. See also `../CLAUDE.md` for the repo-wide architecture (whitelist/session model shared with the client).

## Versioning

Current server version: **1.3.0**, set as `SERVER_VERSION` near the top of `server.py` (logged once at startup). Versioned independently from the client add-on (`client/buildVars.py`'s `addon_version`) — they're separate sub-projects sharing one repo and wire protocol, not a lockstep release train. Tagged/released as `server-vX.Y.Z` (distinct tag namespace from the client's `vX.Y.Z`, to avoid collisions in this shared repo). `1.0.0` was the first formal version — the server carried substantial features (whitelist/quarantine, admin API, controller/observer model, add-on self-update push) before ever being versioned; `1.0.0` marked that first tagged baseline, not a reset. `1.1.0` added the client-release auto-detect and admin-triggered update check; `1.2.0` added the beta (nightly) update channel; `1.3.0` added consent-gated diagnostic log retrieval (see the Architecture bullets below). `1.3.0` tagged/released 2026-08-14 and deployed live; the consent-gated diagnostic log flow was verified end-to-end against production the same day (a one-off raw admin script, not the NVDA GUI - see that bullet's note on `_findNvdaLogPath`).

## Commands

Run and build (via Docker Compose, from this directory):
```bash
# SSL cert/key/chain must exist first, in ./certificate/ (cert, key, chain — PEM files)
docker compose up --build -d
docker compose logs -f
```

Run directly without Docker (e.g. for local debugging):
```bash
pip install -r requirements.txt
python server.py -c certificate/cert -k certificate/key -C certificate/chain [-p 6837] [-m motd_file] [-i ::]
```

There's no linter configured for this sub-project. There is a test suite (`tests/`, `twisted.trial`-based) — see Testing below.

## Testing

```bash
pip install -r requirements.txt   # needs Twisted; the repo's own venv/ may not have it
python -m twisted.trial tests
```
Uses `twisted.internet.task.Clock` (injected via `ServerState(clock=...)`) instead of the real reactor, so quarantine/control-free timers can be advanced deterministically without real sleeps, and a `FakeTransport` (subclassing `twisted.test.proto_helpers.StringTransportWithDisconnection`, adding a no-op `setTcpNoDelay`) in place of real sockets.

## Architecture

A Twisted app split across `server.py` (protocol dispatch: `Handler`/`User`/`RemoteServerFactory`) and `state.py` (session/persisted state: `Channel`/`ServerState`) — split 2026-08-14 per the root `CLAUDE.md`'s "one file, one reason to change" convention; `server.py` re-exports what it needs from `state.py` (`Channel`, `ServerState`, `DATA_DIR`, `ADDON_RELEASE_FILE`, `ADDON_BETA_RELEASE_FILE`, `QUARANTINE_MSG_INTERVAL`, `CONTROL_FREE_MSG_INTERVAL`), so `from server import ServerState` etc. still works unchanged. Key pieces:

- **`Handler`** (a `LineReceiver`, one instance per TCP connection): parses newline-delimited JSON lines and dispatches by `type` field to `do_<type>` methods (e.g. `do_join`, `do_ping`, `do_generate_key`, `do_list_sessions`). Messages with `type` starting with `admin_` are routed through `handle_admin_command` and require `self.user.is_admin`. Any message type not handled explicitly (and not admin-scoped) that arrives from a user already in a channel is instead relayed as-is to the other channel members (`user.channel.send_to_clients`) — the server itself doesn't need to understand remote-control message types like `speak`/`key`/`display`. Before that generic relay path, raw `key` messages carrying F10/Alt+F10 are intercepted by `handle_control_gesture` for the controller take-over/release gesture (see below), and any other master input is gated: dropped (with a throttled `control_denied` reply) unless the sender is the channel's current `controller` or the message type is in `GATE_EXEMPT_MASTER_TYPES` (housekeeping like `set_braille_info`, not real "steering").
- **`User`**: per-connection state (channel membership, `connection_type` = master/slave, admin flag, and the controller-gesture bookkeeping: `held_alt_msg`, `suppress_f10_up`/`suppress_alt_up`, `last_control_denied_at` for throttling). `generate_key()` produces a random legacy pairing code (rate-limited per source IP).
- **`Channel`**: one per session name. Holds joined clients, tracks/broadcasts `client_joined`/`client_left`, and drives the quarantine loop (`send_quarantine_msg` every `QUARANTINE_MSG_INTERVAL` = 5s) while `is_authorized` is false. `send_to_clients` is a no-op if the channel isn't authorized — this is the actual enforcement point that keeps unauthorized traffic from being relayed. Also owns the **controller/observer model**: `self.controller` (a `User` or `None`) — the first master to join an uncontrolled channel is auto-assigned as controller (so a lone master/slave pair, today's only production topology, behaves exactly as before with zero client changes); `toggle_controller(user)` handles take/release/deny for the F10/Alt+F10 gesture; `broadcast_control_changed()` sends `control_changed` to masters only (never slaves, and never folded into `channel_joined`, so old clients that don't understand it just ignore it); while nobody controls and at least one non-controller master is listening, `start_control_free_loop`/`update_control_free_loop` repeat a reminder every `CONTROL_FREE_MSG_INTERVAL` = 30s, mirroring the quarantine-reminder pattern.
- **`ServerState`**: process-wide singleton holding `channels` (active), `authorized_keys` (whitelist, persisted to `data/authorized_keys.json`), `seen_keys` (everything ever seen, persisted to `data/seen_keys.json`), and the admin token (`data/admin.token`, auto-generated on first run via `secrets.token_urlsafe`). All JSON files live under `DATA_DIR` (`data/`, mounted as a Docker volume). Takes an optional `clock` (defaults to the real `reactor`) threaded through the quarantine and control-free timers, so tests can inject a fake one.
- **Admin API** (requires `auth_admin` with the token first): `do_admin_list_channels` (lists whitelist ∪ online ∪ ever-seen, each annotated with online/authorized/client_count, and `versions` - one entry per currently-connected client in that channel, self-reported via that client's `join` message's optional `client_version` field, `None` for a client too old to send it; stored on `User.client_version`, v3.2.2), `do_admin_approve_channel`, `do_admin_remove_channel`, `do_admin_check_for_updates` (v1.1.0 — triggers `update_check.run_scheduled_checks` immediately via `threads.deferToThread`, bypassing the scheduled check's due-gate, and replies with fresh results as `admin_update_check_response`; the admin connection may have dropped by the time the deferred completes, so `_send_update_check_response` swallows send failures rather than erroring). **Non-admin session discovery**: `do_list_sessions` — any already-joined, already-authorized client may ask (no admin token needed) which *other* authorized, online, currently-controllable (has a slave connected) sessions exist, via `list_sessions` → `session_list` (`[{key, client_count, has_controller}]`); this deliberately excludes the requester's own channel and anything offline/unauthorized/slave-less. Writes (approve/block) stay admin-only — only reads were opened up.
- **Server version info** (v1.1.0): `do_get_server_info` → `User.send_server_info()` sends `server_info` (`{version, update_check}`) — **request/response only, not unconditional at `connectionMade`** like `send_motd()`/`send_addon_update()`. A pre-3.2.3 client doesn't know the `server_info` type; an unconditional push would make it `log.error` on every connect (client's `RemoteMessageType(...)` raises `ValueError`), and NVDA plays `error.wav` for any ERROR-level log line (see the client-side `error.wav` feedback-loop lesson - same mechanism, different trigger). Request/response sidesteps this entirely: only a client new enough to send `get_server_info` ever gets a reply. Works whether or not the client has joined a channel yet (`lineReceived` special-cases `get_server_info` in the post-join branch, mirroring `list_sessions`, and it falls through to the generic pre-join dispatch otherwise). Not admin-gated — the server's own version isn't sensitive, and any connected user benefits from being able to check which server they're talking to.
- **Add-on self-update push** (v3.2): `ServerState.get_addon_release()` reads `data/addon_release.json` (`{"version": ..., "url": ...}`) **fresh on every call** — deliberately not cached at startup, so announcing a new client release is just a file write, no server restart. `User.send_addon_update()` sends it as `addon_update` unconditionally at `connectionMade`, alongside `send_motd()` — before join/auth, same reasoning as MOTD: an outdated/quarantined client is exactly the one that needs telling. A missing or malformed file degrades to "push nothing" and must never raise there. This file is now normally kept up to date *automatically* (see the client-release auto-detect bullet below) — `set_addon_release.py` still exists for a manual override/rollback to a specific version.
- **Protocol versioning**: `protocol_version` message sets `Handler.protocol_version`; this changes the shape of a few messages (`channel_joined`/`client_joined`/`client_left` carry richer per-client dicts, via `User.as_dict()`, from v2 onward) and whether `origin` is echoed back on relayed messages.
- **Server self-update check** (v1.0.0, `update_check.py`) — the server checking *its own* GitHub releases for a newer `server-vX.Y.Z` tag (distinct from `addon_update` above, which is the server telling *clients* about a newer client release). Deliberately check-only: it logs and persists the result to `data/server_update_check.json`, never downloads or applies anything, and never restarts the process — this is a live daemon relaying active sessions, so touching it automatically is out of scope. Two entry points: `server.py`'s `_scheduled_update_check`, ticked hourly by a `LoopingCall` but only actually calling GitHub when `update_check.is_check_due()` says the configured interval (`data/server_config.json`'s `update_check_interval_hours`, default 24, set via `set_update_check_interval.py`, read fresh — no restart needed) has elapsed; and `check_server_update.py`, a standalone CLI script for an immediate on-demand check ("check right now"), sharing the same state file so it doesn't get immediately re-done by the scheduled loop. `update_check.py` itself has no Twisted dependency (so the CLI script doesn't need `pip install -r requirements.txt`) and the real HTTP call is always routed through `threads.deferToThread` when called from the reactor thread — a blocking `urllib` call directly in a `LoopingCall` callback would stall relaying for every connected client for as long as the request takes.
- **Client-release auto-detect** (`update_check.check_for_client_update`, same module/schedule as the bullet above) — unlike the server self-check, this one *applies* what it finds: it looks for the latest **official** (non-prerelease, non-draft — GitHub's own semantics, checked via each release's `prerelease`/`draft` flags) client `vX.Y.Z` release with a `.nvda-addon` asset, and if it's strictly newer than what's currently in `data/addon_release.json`, atomically overwrites that file — the same write `set_addon_release.py` does by hand. Never downgrades. Safe to auto-apply (unlike the server self-check) because every actual safety net already lives client-side: strictly-newer-only, never auto-downgrade, never auto-restart NVDA (see `client/CLAUDE.md`'s `addon_update.py` entry). Run by the same `run_scheduled_checks`/`check_server_update.py` entry points as the server self-check, under the one configured interval.
- **Beta (nightly) update channel** — `update_check.check_for_client_beta_update` mirrors the bullet above, but for the rolling `nightly` tag (`../make_nightly.sh`), writing `data/addon_beta_release.json`. Identified by **tag name**, not by ranking versions — `nightly` isn't semantically versioned (its manifest version is a build timestamp), so unlike the stable check there's no "is this newer" gate; it always overwrites when a `nightly` release with a usable asset exists, and the actual version string comes from that asset's filename (`remote-<version>.nvda-addon`) rather than trying to parse it out of release metadata. `User.send_addon_update()` only ever reads this file for a connection with `allow_beta_updates=True` (self-reported on `join`, off by default) — falls back to the stable file if no beta build is available yet, never the reverse. Because `allow_beta_updates` isn't known until `do_join` (after the unconditional `connectionMade`-time `send_addon_update()`, which can therefore only pick stable), a beta-opted-in client gets `addon_update` pushed *twice* on connect: once stable (before join), once beta (right after join sets the flag) — harmless, client-side gating already tolerates a repeated/superseded push, but not simultaneous: `addon_update.py`'s `_checking` flag serializes downloads, so on a client's *first* connect after opting in, the stable push (arriving first) wins the flag and the immediately-following beta push is silently dropped, not queued — the nightly only actually installs starting from the *next* connection/reconnect, not the one where the checkbox was just ticked. `check_for_client_beta_update` runs unconditionally alongside the other two checks in `run_scheduled_checks`, regardless of whether anyone is currently opted in, so the file is already fresh the moment someone does opt in. Deliberately **not** added to `admin_update_check_response` (`do_admin_check_for_updates`'s reply) — that would be a new field on an already-shipped message with a fixed-signature client handler, the exact hazard the `server_info` bullet above was caught and fixed for; a nightly's status is visible via the server log instead.

- **Consent-gated diagnostic log retrieval** (v1.3.0) — `do_admin_request_logs` (admin-only) asks a specific online session's slave connection for permission to upload its NVDA log. Split into `state.py`'s `PendingLogRequest` (who asked, who's being asked, the pending timeout `DelayedCall`) and `Channel.pending_log_request` — see that class's docstring for the full design. The critical property: while a request is pending, `Handler.lineReceived` denies **all** master input on that channel, including the current controller and the F10/Alt+F10 take-over gesture, not just non-controllers — this fork's remote key control uses real Win32 `SendInput` (`localMachine.sendKey` → `input.send_key` client-side), so an ordinary modal consent dialog does not, by itself, stop an already-connected controller from synthesizing a "Yes" onto their own consent prompt. The gate must close *before* `request_log_access` is ever relayed to the slave (`do_admin_request_logs` sets `channel.pending_log_request` first, sends second) — closing it after would leave a window where a `key` message already in flight from the controller could still land on an already-showing dialog. Only the last `LOG_TAIL_MAX_BYTES` (client-side, `diagnostics.py`) of the log is ever sent, and the server independently caps what it writes (`state.py`'s `MAX_DIAGNOSTIC_LOG_BYTES`) as a backstop against a modified client — both exist so a single upload never risks exceeding `Handler.MAX_LENGTH` (20MB/line), avoiding the need for a chunking protocol. `save_diagnostic_log` writes to `data/diagnostic_logs/<session>_<UTC timestamp>.log`. A pending request times out after `LOG_REQUEST_TIMEOUT` (60s) if unanswered, and is cleared immediately if either side disconnects mid-request — notably, the admin disconnecting is detected in `User.connection_lost()` by scanning all channels for a `pending_log_request.admin is self`, not via `Channel.remove_connection`, because the requesting admin is typically *not* a member of the target channel at all (admin auth is piggybacked on that admin's own home connection, per `client/CLAUDE.md`'s `_get_active_transport`) — `Channel.remove_connection`'s cleanup only ever fires for a channel the disconnecting user was actually in.

## Notes for changes

- `Channel.remove_connection` tears down (and deregisters from `ServerState`) a channel once its last client leaves — channels are not persistent objects, only the whitelist/seen-keys entries are. It also clears `controller`/stops the control-free loop if the leaving client was the controller.
- Any new client-facing capability should be added as a new top-level `do_<type>` on `Handler` or a new method on `ServerState`/`Channel`, following the existing pattern — not folded into the admin-only path unless it should actually require the admin token (see `do_list_sessions` for the "open read, admin-only write" split).
- **Backward compatibility is load-bearing**: some already-deployed clients can't be updated in lockstep with the server (see the deferred per-user-visibility note in `../CLAUDE.md`). Never add a required field to an existing message type's payload (e.g. `channel_joined` must never gain a `controller` field — old clients have fixed, non-`**kwargs` handlers and would break). New information belongs on an entirely new message type - but **"an unrecognized client silently ignores it" is only true for messages the server sends *to masters only*, or in reply to a request only a new-enough client would send** (`control_changed`/`control_denied` go to masters, which in this fork's actual deployments have always been the same up-to-date build as the slave; `session_list` only ever replies to a `list_sessions` a new client sent). An unconditional push to *every* client - like `motd`/`addon_update` - is only safe once, retroactively, once every deployed client is known to already understand the type; sending one for the first time to a still-mixed fleet makes an old client's `transport.py` hit `RemoteMessageType(obj["type"])` → `ValueError` → `log.error` → an audible `error.wav` on every connect (caught before shipping for `server_info`, fixed by making it request/response instead - see that bullet above).
