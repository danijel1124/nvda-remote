# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Client-specific guidance. See also `../CLAUDE.md` for the repo-wide architecture (whitelist/session model shared with the server).

## Commands

Build the add-on (needs `scons` and `markdown` installed, e.g. in the repo's `venv`):
```bash
scons
```
Produces `remote-<version>.nvda-addon` (currently `remote-3.2.4.nvda-addon`) in this directory. `scons` is also the default SConstruct target — CI (`../.github/workflows/main.yml`, at the *repo root*, not under `client/` — GitHub Actions only discovers workflows at the repository root, so it must live there even though this sub-project used to be the whole repo) runs `pip install scons markdown && scons` (via `working-directory: client`) on every push/PR to `master`/`main`, and on any tag push additionally creates a GitHub Release with the built `.nvda-addon` attached.

Other scons targets:
```bash
scons pot        # extract translatable strings to build/*.pot
scons mergePot    # merge extracted strings into existing locale .po files
```

Linting: a flake8 config exists at `flake8.ini` (NVDA add-on template config: tabs, max-line-length 110, max-complexity 15) but is not wired into scons or CI — run manually, e.g. `flake8 --append-config=flake8.ini addon/globalPlugins/remoteClient`.

`tests/` holds logic-level regression tests for `menu.py`/`dialogs.py`/`connection_info.py`/`addon_update.py` (item-enablement state machine, session picker, config round-trip, self-update version-gating), run with the *system* `python3` (needs `configobj`, not NVDA-only):
```bash
python3 -m unittest discover -s tests -v
```
It works by installing minimal stand-ins for `wx`/`gui`/`addonHandler`/`logHandler`/`globalVars` in `sys.modules` and importing the target submodules directly, bypassing `remoteClient/__init__.py` (which pulls in `client.py`). `client.py` itself (and anything that imports it) cannot be unit-tested outside a real NVDA process — it imports `ctypes.wintypes`, `api`, `braille`, `core`, `keyboardHandler`, `winUser`, `utils.security`, none of which exist as installable packages — so its logic has to be verified by careful reading (and, ultimately, a live run against the control server) rather than automated tests.

Change the add-on version in `buildVars.py` (`addon_info["addon_version"]`), not in `sconstruct`.

## Architecture

All product code lives in `addon/globalPlugins/remoteClient/`, an NVDA global plugin package. `__init__.py` is the NVDA entry point: it instantiates a single `RemoteClient` and registers global gestures (`ctrl+shift+NVDA+c` = generate/copy link, `alt+NVDA+pageUp` = connect, `alt+NVDA+pageDown` = disconnect, `f11` = toggle sending keyboard input to the remote machine).

Connection roles: a session is either **master** (this machine controls a remote one) or **slave** (this machine is being controlled) — `ConnectionMode` in `connection_info.py`. `RemoteClient` (`client.py`) can hold a `masterSession`/`masterTransport` and a `slaveSession`/`slaveTransport` concurrently and independently (they're separate TCP connections); most of the day-to-day master/slave asymmetry lives in `session.py`.

Layering, roughly bottom-up:
- **`transport.py`** — `Transport`/`TCPTransport`/`RelayTransport`: raw framed JSON-over-TLS socket handling, a reconnect thread (`ConnectorThread`), and a pub/sub-style `registerInbound(RemoteMessageType, callback)` mechanism used by everything above it. `RelayTransport.create()` builds one from a `ConnectionInfo`.
- **`protocol.py`** — `RemoteMessageType` enum, the single source of truth for wire message type names (also documented in `protocol.md`); `SERVER_PORT` (6837) and the `nvdaremote://` URL prefix.
- **`session.py`** — `RemoteSession` base plus `MasterSession`/`SlaveSession`: wires transport inbound messages to actual NVDA behavior (speaking, braille, patched input) via `nvda_patcher.py` (`NVDASlavePatcher`/`NVDAMasterPatcher`, hooking NVDA's speech/braille pipeline) and `localMachine.py` (`LocalMachine`, the local audio/braille/clipboard sink used by a slave session).
- **`client.py`** — `RemoteClient`: top-level orchestrator. Owns connect/disconnect flows for both roles and the low-level keyboard hook thread (`keyboard_hook.py`, forwards keys to the remote machine while `sendingKeys` is true, toggled by F11 via `toggleRemoteKeyControl`). `keyboard_hook.py`'s own exception logging must go through `logHandler.log` (what everything else in this addon uses), never a bare `logging.getLogger(...)` + `StreamHandler` - a windowed `NVDA.exe` has no console attached to `sys.stdout`, so anything logged that way is silently discarded. That was the bug for a while: `keyboard_proc`'s callback loop fails *open* on an exception (a buggy callback must never be able to lock up the entire keyboard system-wide - the key just passes through to the local machine unblocked instead), and with the exception going nowhere visible, that failure mode looked identical to "remote key control silently does nothing" with no diagnostic trail at all.
  A second, related silent-failure mode fixed in v3.3.2: `KeyboardHook.__init__` never checked `SetWindowsHookExW`'s return value. If that WinAPI call fails, `keyboard_proc` is never invoked by Windows at all - no exception, no callback, nothing for the exception-logging fix above to catch - while `toggleRemoteKeyControl` still flips `sendingKeys` and announces "Controlling remote machine.", since that announcement only reflects server-side controller state, not whether the local hook is actually intercepting anything. Now logs the failure (`ctypes.get_last_error()`, via a `use_last_error=True` handle so an intervening Win32 call from elsewhere can't clobber the read) and speaks an audible error from the hook thread. Also now logs on the *success* path too, so a future log fetch can tell "hook installed fine, bug is elsewhere" apart from "hook never installed" - previously both looked identical (silent). Root cause of the original F11 bug report is not fully confirmed (Linux dev environment can't exercise real `ctypes.windll` WinAPI calls) - this and the exception-logging fix are both real, defensible fixes on their own merits; whichever (if either) was the actual cause, the next reproduce-then-fetch-log cycle should now be conclusive either way.
- **`admin_client.py`** (split from `client.py` 2026-08-14, per the root `CLAUDE.md`'s "one file, one reason to change" convention) — `AdminClientMixin`, mixed into `RemoteClient` (not composed as a separate object), holding all admin-protocol plumbing (`send_admin_*`/`handle_admin_*`, `_get_active_transport`, `_maybe_reauth_admin`, used by `server_admin_gui.py`). Mixed in rather than composed so every existing call site (`self.client.send_admin_auth(...)` etc.) kept working unchanged - only `client.py` itself needed to change, to call `_init_admin_state()`/`clear_admin_transport_if()` at the right points.
- **UI**: `menu.py` (`RemoteMenu`, the Tools → Remote submenu — item enablement is driven by `handleConnected`/`handleConnecting`, tracking master/slave connectedness separately since the two roles are independent, concurrent connections), `dialogs.py` (`DirectConnectDialog` — connects as slave only, no master/slave choice; `ControlAnotherComputerDialog` — plain `wx.ListBox` picker populated from a `list_sessions`/`session_list` round-trip, for switching to controlling another already-online machine without reconnecting; `CertificateUnauthorizedDialog`), `server_admin_gui.py` (tabbed admin GUI: token management + session/whitelist management, talks to the server's `admin_*` protocol messages), `settings_panel.py` (NVDA Settings integration).
- **`configuration.py`** — `configobj`-based `remote.ini` handling with a strict configspec. Notably: `key` (session name) is force-set to `socket.gethostname()` on load, overriding anything else; `migrate_config()` handles upgrades between config versions (including legacy admin-token migration, prompting via a dialog); `minify_config()` strips config entries not present in the configspec (wired to the menu's "Clean up configuration..." item).
- **`secureDesktop.py`** — keeps a slave session alive across NVDA's secure-desktop switch (UAC prompts, lock screen) by relaying through a `bridge.py`/local relay (`server.py` in this package — a small `LocalRelayServer`/`Client` pair, distinct from the top-level `server/` project — used only for this loopback secure-desktop bridging, not for real remote relaying).
- **`url_handler.py`** — registers the `nvdaremote://` URL protocol (Windows registry) so links can trigger `RemoteClient.verifyAndConnect`.
- **`diagnostics.py`** (`SlaveDiagnostics`, v3.3.0 client / v1.3.0 server) — this machine's (slave) side of the consent-gated diagnostic log flow: `handleRequestLogAccess` shows a Yes/No dialog when the server's admin asks (`request_log_access`), reads and tail-caps this machine's NVDA log (`LOG_TAIL_MAX_BYTES`, located via `_findNvdaLogPath` walking log handlers rather than a guessed path) only if granted, and sends it back (`log_upload`). `_findNvdaLogPath` checks both `logHandler.log.handlers` and `logHandler.log.root.handlers` — the first real production request (2026-08-14) came back "could not be located" because NVDA's `logHandler.initialize()` attaches the FileHandler via `log.root.addHandler(...)`, i.e. to the stdlib root logger, not to `log` (a named child logger) itself; `log.handlers` alone is always empty. Fixed same day, in v3.3.1. One instance per `SlaveSession` (wired in there, never on a transient master connection - a machine's own log is only ever asked for on its "home" connection). The actual protection against an already-connected controller auto-approving its own request is server-side, not this dialog's modality - see `server/CLAUDE.md`'s matching entry and `server/state.py`'s `PendingLogRequest`.
- **Client-version self-report** (v3.2.2) — `transport.py`'s `RelayTransport.onConnected` sends its own `addonHandler.getCodeAddon().version` as an extra `client_version` field on the outgoing `join` message. Admin-visibility only (shown as a new "Add-on version" column in `server_admin_gui.py`'s session list, sourced from `do_admin_list_channels`'s new `versions` field, one entry per connected client in that channel) - deliberately *not* added to `User.as_dict()`, so it's never relayed into `channel_joined`/`client_joined`, which real peer clients (not just the admin GUI) parse and could have fixed handlers that don't tolerate an unexpected field. An older client simply doesn't send it; the server reports `None`/`?` for that connection rather than erroring.
- **`addon_update.py`** (v3.2) — self-update, pushed by the server via `addon_update` (registered in `RemoteSession.__init__`, so it fires on both master and slave connections). `last_handled_version`/`last_handled_failed` in config are the *primary* gate (checked before comparing against the installed version), not just a dedup convenience: `addonHandler.getCodeAddon().version` still reports the old version until NVDA is restarted to complete a pending install, so gating on the installed version alone would re-download and reinstall the same update on every `ConnectorThread` reconnect. Downloads (plain `urllib`, normal cert validation — deliberately not inheriting the relay transport's `insecure`/trust-fingerprint state) and installs (`addonHandler.AddonBundle`/`installAddonBundle`, the two public entry points — no private `gui.addonGui` helpers, since none of this can be import-tested outside NVDA) happen on a background thread; NVDA is never auto-restarted, only announced — a screen-reader user losing NVDA mid-task without warning is worse than a delayed update. Never auto-downgrades: only a strictly newer version triggers anything. `installAddonBundle` only extracts the new version to a pending-install path — it does *not* remove a same-ID existing install on its own (confirmed by reading NVDA core's source), so the old add-on's `requestRemove()` must be called too, same as `gui.addonGui.installAddon` does. After a successful install, `_announceInstalled` offers (not forces) an immediate restart via a Yes/No dialog (`core.restart()` on Yes) — still never auto-restarts without the user's explicit choice, just makes "restart now" one click instead of a manual detour.
- **Server version visibility** (v1.1.0 server / v3.2.3 client) — `transport.py`'s `onConnected` sends `get_server_info` right alongside `protocol_version`/`join`; the server replies with `server_info`. **Deliberately request/response, not an unconditional push** like `addon_update`/`motd`: an old client (pre-3.2.3) has no `server_info` in its `RemoteMessageType` enum, and an unrecognized type raises inside `transport.py`'s `parse()`, logged via `log.error` — which NVDA turns into an audible `error.wav` on every connect (see the `error.wav` feedback-loop lesson below; this is the same root cause, a different trigger, caught before it shipped this time). Since only a client new enough to send the request would ever get a reply, no old client is ever affected. Not admin-gated (server version isn't sensitive), stored on `RemoteSession` (`serverVersion`/`serverUpdateCheck`, `session.py`'s `handleServerInfo`). Surfaced two ways: `menu.py`'s "Relay server information" item speaks it on demand (deliberately not a proactive announcement/dialog on every connect — too intrusive for something this low-stakes); `server_admin_gui.py` shows it in a label in the Token Management tab, plus a "Check for updates now" button (`admin_check_for_updates` → `admin_update_check_response`, admin-only, forces an immediate GitHub check bypassing the server's daily due-gate, also drives the server's client-release auto-detect — see `server/CLAUDE.md`'s `update_check.py` entry). That button's handler builds the label from the fresh response directly rather than re-reading the session's cached (and by then stale) `serverUpdateCheck`.
- **Opt-in beta (nightly) update channel** — off by default; a client must explicitly opt in via `settings_panel.py`'s "Allow beta (nightly, untested) updates" checkbox (`configuration.py`'s `[addon_update] allow_beta_updates`) before it can ever receive a nightly build. Self-reported on `join` (like `client_version`), read via `.get('allow_beta_updates', False)` server-side — an old client simply never sends it, which is indistinguishable from opting out. `addon_update.py`'s `_parseVersion`/`_isNewer` had to become nightly-format-aware to make this actually work: a nightly's manifest version (`nightly-YYYYMMDDHHMMSS`, see `../make_nightly.sh`) doesn't parse as dotted-numeric, so without this a beta-opted-in client would never detect a nightly as "newer" and the checkbox would silently do nothing. Parses into a `(rank, payload)` tuple — rank 0 for stable dotted-numeric, rank 1 for nightly — so any nightly always outranks any stable version (built from current HEAD, which is always ≥ the latest tagged stable release) and two nightlies compare by their zero-padded timestamp suffix. By rank alone this would make unchecking the box a one-way door (a stable release could never outrank an already-installed nightly, so a client that tried beta once would never receive another stable update again); `_checkAndOffer` therefore carries a deliberate, narrow exception — when beta is off and the pushed version is stable, each of its two gates (`last_handled_version`, installed version) is bypassed *only* if that gate's own operand is still a nightly, not both together, since `installedVersion` keeps reporting the old nightly until NVDA actually restarts (a restart the client only offers, never forces) while `last_handled_version` flips to the stable string as soon as it's handled — gating per-operand is what stops that pending-restart window from turning into a re-download/re-nag loop on every reconnect. See `server/CLAUDE.md`'s `update_check.py`/`addon_beta_release.json` entry for the server side, including why "opt in, reconnect" doesn't land the nightly on that same connection — the stable push (sent before join) wins `addon_update.py`'s `_checking` flag and the beta push (sent right after join) is dropped, not queued, so the nightly only installs starting from the connection *after* the one where the checkbox was ticked.

## Notes for changes

- Never delete existing GUI functionality (e.g. in `server_admin_gui.py`) when extending it — add to it, keep all features working.
- After changing anything under `addon/globalPlugins/remoteClient/`, rebuild with `scons` before considering the change done.
- **`transport.transportClosing`/`transportDisconnected` are two different events** (deliberate close vs. unexpected drop) and code needs to react to both, not just the one that's easiest to trigger in manual testing. Two real bugs so far had the same shape: a handler existed but was registered only on `transportClosing`, so an unexpected drop silently skipped cleanup. One (`MasterSession._resetControlState`) was caught in review; the other (`SlaveSession.handleTransportDisconnected`) shipped and was found via a real user's NVDA log — it left `nvwave.decide_playWaveFile` (the outbound wave-relay hook) registered after a drop, so NVDA's own `error.wav` (played for any ERROR-level log entry) kept getting relayed through the disconnected transport, which logged its own ERROR, triggering another `error.wav`, forever - 483 occurrences in one captured log. Fixed in 3.2.1 by registering `handleTransportDisconnected` on `transportDisconnected` (it wasn't registered anywhere at all) and downgrading `transport.py`'s "attempted to send while not connected" from `log.error` to `log.warning` as defense in depth, since ERROR-level logging is uniquely dangerous here (it's audible and self-relayable), not just noisy.
- `server.py`'s (the secure-desktop bridge, not the top-level relay) `ssl.wrap_socket()` was removed in Python 3.12 - newer NVDA builds crashed with `AttributeError` on every secure-desktop transition. Use `ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)` + `load_cert_chain` + `context.wrap_socket(sock, server_side=True)` instead.
